Part I

Building a VLM from a plain LLM

nanoVLM is ~750 lines of pure PyTorch: a ViT image encoder, a SmolLM2 language decoder, and a tiny projector that bridges them. We build it bottom-up.

Section 1

The splice, precisely

§1The whole multimodal change lives in one method, _replace_img_tokens_with_embd: build a boolean mask of image-token positions and copy the projected image vectors into exactly those rows.

A decoder LLM maps token ids → embeddings [B,T,D] → transformer blocks → logits. To make it multimodal you reserve a placeholder token, <image>, repeat it 64 times per image, and after embedding the text you overwrite those 64 rows with 64 vectors made from the pixels. The decoder is untouched.

One flag makes it work: nanoVLM's language model has an lm_use_tokens switch. As a normal LLM it takes token ids and returns logits; as a VLM backbone it takes embeddings and returns hidden states — so you can feed it a mix of text and image vectors.

Go deeper: trace the shapes through one forward

Batch B=2, sequence T=512, width D=576, 64 image tokens/image. The head is applied only to compute the loss; a VLM backbone otherwise stays in embedding space.

Section 2

The language backbone

§2The static config ships placeholder dims (960 / 15 heads / 32 layers). from_pretrained overwrites them to the real SmolLM2-135M: 576 / 9 heads / 30 layers. The checkpoint is the source of truth for shape.

The backbone is a modern (Llama-style) decoder: RMSNorm, rotary positions, grouped-query attention, a gated MLP, and a tied head. Thirty identical blocks stacked on a residual stream do all the work — so we look at the block whole first, then open each piece.

The block, assembled

§2Every sub-layer reads from and writes back to a shared residual stream. Because each only adds to it, gradients flow straight down the skip path — the reason a 30-layer transformer trains at all.

A block is two pre-norm residual sub-layers — normalize, transform, add back — wrapped around the two operations we unpack in this section: attention, which mixes information across token positions, and a gated MLP, which processes each token on its own.

res = x;  x = res + attn(rmsnorm(x), cos, sin, mask)   # attention sub-layer — mixes across positions
res = x;  x = res + mlp(rmsnorm(x))                    # feed-forward sub-layer — per position

The feed-forward is a gated MLP (SwiGLU): two parallel projections up to a wider dimension, one passed through a SiLU gate, multiplied elementwise, then projected back down:

SwiGLU(x)=Wdown(SiLU(Wgatex)⊙Wupx)

The gate lets the network modulate its own signal per-channel — and this MLP is where most of a block's parameters live (the budget in §6). Click a stage, or play a token through the block:

Go deeper: the residual stream as a communication channel

A useful mental model: the residual stream is a shared bus of width 576 that every layer reads from and writes to. Attention moves information between token positions; the MLP processes it within a position. Because writes are additive, later layers can read what earlier layers deposited, and a sub-layer that has nothing to add can output ~0 and leave the stream unchanged. Pre-norm (normalizing the input to each sub-layer, not its output) keeps the stream's scale from exploding across depth, which is what makes very deep stacks trainable without careful warmup tricks.

Go deeper: embeddings, weight tying & the extended vocabulary

The first and last layers are a matched pair. The token embedding is a lookup table [vocab×576] turning ids into vectors; the head projects the final hidden state back to [576×vocab] logits. nanoVLM ties them — head.weight = token_embedding.weight — halving those 28M parameters and coupling "how a token looks going in" with "how it's scored coming out".

To host images, the VLM grafts 66 new tokens onto SmolLM2's 49,152-token vocabulary (the <image> placeholder plus tile markers), giving 49,218. The pretrained rows are copied in; the 66 new rows are freshly initialized and learned during training. The embedding matrix is the one place the "language" model gains genuinely new, vision-specific vocabulary.

Self-attention

Now the attention sub-layer we deferred. Each token forms a query Q; it scores every token it may attend to via a dot product with their keys K, softmaxes those scores into weights, and mixes their values V:

Attention(Q,K,V)=softmax(QK⊤dk)V

In the decoder a causal mask forbids looking right; in the ViT (Part I §3) there's no mask — vision is bidirectional. See it:

Rotary positions (RoPE)

There are no learned position vectors. Each query/key is rotated by an angle proportional to its position, so an attention score depends only on the relative distance between two tokens.

Go deeper: the rotation, written out

RoPE applies a position-dependent rotation to q and k before the dot product. In 2-D, for position m and frequency ω:

qm=(cosmω−sinmωsinmωcosmω)q

The code realizes this as q·cos + rotate_half(q)·sin. The magic: for two positions m, n the rotated dot product depends only on m−n — so the model generalizes to relative offsets it never saw at those absolute indices.

Grouped-query attention

Full attention keeps one key/value per query head. GQA keeps fewer KV heads and shares them across groups of query heads — big cache savings for almost no quality loss. SmolLM2-135M uses 9 query heads served by 3 KV heads.

The KV-cache

Generating one token at a time, you don't re-attend over the whole prefix each step. The cache stores past keys/values so a new token computes only its own K/V and attends against the stored ones.

The attention-variants landscape

GQA is one point on a spectrum that trades KV-cache size against expressiveness. The cache is what you must store per token to avoid recomputation (§2 KV-cache); shrinking it is the difference between a model that serves long contexts cheaply and one that doesn't.

Go deeper: MLA and FlashAttention, a little more carefully

MLA (Multi-head Latent Attention, DeepSeek). Instead of caching K and V per head, MLA caches a single low-rank latent ct per token and reconstructs each head's K,V by up-projection at attention time. The cache shrinks to the latent width (often <10% of MHA) while keeping near-MHA quality — it decouples cache size from head count. It pairs with a RoPE-compatible split so positions still work.

FlashAttention changes nothing mathematically — it computes the exact same softmax. What it changes is memory traffic: the naive kernel materializes the full T×T score matrix in slow HBM; FlashAttention tiles Q/K/V, keeps the running softmax in fast on-chip SRAM, and never writes the big matrix out. Result: linear memory in T and a large speedup — which is why enabling attn_implementation="flash_attention_2" (as this repo's SFT does) matters even though the outputs are identical.

Section 3

The vision backbone

§3Unlike the decoder, the ViT attends bidirectionally and uses LayerNorm + learned position embeddings, not RMSNorm + RoPE.

A Vision Transformer (SigLIP2-base/16-256) cuts a 256×256 image into 16×16 patches with a single strided convolution, adds position embeddings, and runs 12 transformer blocks. Out comes 256 patch vectors of width 768. Here's the grid it sees:

Same skeleton, different dialect

The vision and language towers share the transformer skeleton but differ in nearly every detail — because images and text have different structure. Reading this table is the fastest way to internalize both architectures at once:

AspectViT tower (SigLIP2)LLM tower (SmolLM2)
attentionbidirectional (no mask)causal (can't see the future)

And the vision tower is specifically SigLIP2. Where CLIP's contrastive loss softmaxes over every image–text pair in a batch (so the batch is a global normalizer), SigLIP replaces it with a simple pairwise sigmoid loss — each pair judged independently. That's cheaper, scales to larger batches, and yields stronger features for small encoders. nanoVLM keeps the vit_cls_flag=False setting: no CLS token, so all 256 patch vectors survive — exactly what the projector needs to preserve the spatial grid.

Go deeper: patch embedding, and loading pretrained weights into from-scratch code

The "patchify" step is one strided convolution: a Conv2d with kernel = stride = 16 slides over the image, and each output pixel is one patch's 768-dim embedding — [3,256,256] → [768,16,16] → flatten → [256,768]. No overlap, no separate linear layer.

nanoVLM re-implements the ViT and LM from scratch, then loads the pretrained SigLIP2 / SmolLM2 weights into its own modules with a name-mapping dict. One wrinkle: HuggingFace stores Q, K, V as three separate matrices, but nanoVLM fuses them into one qkv_proj, so the loader concatenates them: qkv = cat(q_weight, k_weight, v_weight). This "weight surgery" — mapping names, fusing/splitting projections, extending the embedding for new tokens — is the unglamorous glue that lets a clean from-scratch model inherit a pretrained one.

But the LLM wants width 576, and 64 vectors per image, not 256. Reconciling (256, 768) → (64, 576) is the projector's job (§4).

Where the boundary comes from: the chat template

The mask isn't guessed — it's found. The tokenizer's chat template wraps each turn in role markers, e.g. <|im_start|>user … <|im_end|> then <|im_start|>assistant. The collator locates that last assistant marker and supervises everything after it. The special tokens are the supervision boundary.

Section 7 · SFT

Supervised fine-tuning

Same recipe as §5, new task: show the model (receipt, prompt) → gold JSON and train it to reproduce the gold tokens — same completion-only, vision-masked loss, now as a LoRA adapter (§LoRA).

The loss, up close: cross-entropy

What is actually minimized is the token-level cross-entropy (negative log-likelihood) over the answer positions only — the same objective as Part I §6, and the whole of SFT:

ℒSFT=−1|𝒮|∑t∈𝒮logpθ(yt∣x<t)

At each answer position the model produces a distribution over the whole vocabulary; the loss reads off the probability of the one gold token and charges −logp. Drag the probability the model assigns that gold token and watch the penalty move along the −log curve:

how it serves the objective
Cross-entropy is mode-seeking on a single correct answer: it only rewards probability on the gold token, which is exactly right when the target is a fixed string (the gold JSON). It is also why masking matters — the pressure lands on the answer, not on re-predicting the receipt image or the schema.

What a training run actually looks like

The loop is standard but the settings matter: a warmup-then-cosine learning rate, bf16, gradient accumulation to fake a big batch, gradient checkpointing to fit memory, and a fused cross-entropy so the 248k-token vocabulary logits never fully materialize.

Go deeper: why liger fused cross-entropy, and gradient checkpointing

The last layer projects each of ~thousands of positions to a 248,077-way vocabulary. Storing those logits and their softmax gradients is gigabytes. A fused CE (liger kernel) computes the loss and gradient in chunks without ever holding the full logits tensor — often the difference between fitting and OOM on a 4B VLM. Gradient checkpointing trades compute for memory the other way: it discards activations on the forward pass and recomputes them during backward, cutting activation memory at ~30% more compute. (GRPO/GKD sometimes turn it off because it disables the KV-cache during on-policy generation, which is far more expensive.)

result
SFT does most of the work. Macro pair_f1 jumps 0.795 → 0.900 on the 4B; a raw Gemma base that emits zero valid JSON goes 0.00 → 0.86.

Section 8 · GRPO

Reinforcement learning from a local reward

§8The reward is deterministic and local — no LLM judge. Every JSON is flattened to a multiset of (leaf-key, value) pairs, making SROIE's flat fields and CORD's nested items comparable with one code path.

SFT imitates one gold answer. GRPO samples several completions per prompt, scores each with a reward, and pushes the policy toward the above-average ones. The reward blends validity, field coverage, and value correctness:

0.30·parsable + 0.50·field_f1 + 0.20·value_acc

Type a prediction and watch it — the scoring is the exact trainer algorithm, ported to JavaScript:

The scalar becomes a gradient through the group-relative advantage: for a group of G completions, normalize each reward within the group,

Ai=ri−mean(r)std(r)

The group mean is the baseline — no separate value network needed. Those advantages enter GRPO's clipped surrogate objective (with β=0 here there is no KL-to-reference term):

𝒥(θ)=𝔼[1G∑i=1G1|oi|∑tmin(ρitAi,clip(ρit,1−ε,1+ε)Ai)]

where ρit=πθ/πold is the importance ratio. The sign of the advantage sets the direction — raise the probability of tokens from above-average completions, lower the below-average — and the clip bounds how far a single update may move the policy. Go deeper: decoding — how those completions are sampled

Each rollout is autoregressive generation: a multimodal prefill (splice image tokens, run the decoder once to fill the KV-cache) then a decode loop that samples one token at a time. Sampling is shaped by temperature (flattens/sharpens the distribution), top-k (keep the k likeliest), and top-p (keep the smallest set with cumulative prob ≥ p); greedy = argmax. GRPO wants diversity across its 8 samples, so it samples with temperature rather than greedily — low diversity is one more way the advantage collapses.

Section 9 · Distillation

On-policy distillation (GKD)

§9Both models are the same Qwen3.5 family — identical 248,077-token vocab and identical image tokenization (a receipt → the same 475 <image_pad> tokens). That's what makes one input_ids scorable by teacher and student.

We have a strong 4B extractor. Can a 5× smaller 0.8B student inherit most of it? In on-policy GKD the student samples a completion; both student and the frozen 4B teacher score those tokens; and a generalized Jensen–Shannon divergence pulls the student's distribution toward the teacher's. The teacher's full distribution is a far richer signal than one gold label.

The loss: matching a distribution, not a label

SFT's target is a one-hot vector — all mass on the gold token. Distillation's target is the teacher's entire next-token distribution, and the loss is a KL divergence that pulls the student s onto the teacher t:

KL(t∥s)=∑vt(v)logt(v)s(v)

The teacher's small probabilities on plausible tokens — its "dark knowledge" — are exactly the signal a one-hot label discards. Toggle the target the student is trained against:

The β knob picks the divergence's character. See what it does to a student trying to match a two-mode teacher:

ℒ=βKL(t∥s)+(1−β)KL(s∥t)

with t the teacher and s the student distribution over the next token. β=0.5 is the symmetric JS divergence.

Go deeper: forward vs reverse KL, and why on-policy

Forward KL KL(t∥s) (β→1) is mode-covering: the log(t/s) term explodes wherever the teacher has mass but the student assigns ≈0, forcing the student to cover every teacher mode — safe, but it can smear probability onto unlikely tokens. Reverse KL KL(s∥t) (β→0) is mode-seeking: the student may drop teacher modes as long as its own mass sits under the teacher — sharper, but it can collapse. The generalized JSD at β=0.5 interpolates. On-policy means the divergence is measured on tokens the student itself sampled, so training fixes the student's own mistakes rather than teacher text it would never produce — the reason on-policy GKD beats plain sequence-level distillation on a fixed teacher corpus.

Section 9.5

Multimodal RoPE — the plumbing nobody warns you about

§9.5This is what "RL/distillation on a brand-new VLM" actually looks like: you fix a positional-encoding bug inside someone else's trainer.

A text LLM's RoPE indexes one dimension: position 0,1,2,… But an image is 2-D. Qwen3.5 uses multimodal RoPE (M-RoPE): every token gets a 3-D position (t,h,w) — temporal, height, width — so image patches carry their grid location and text advances in time. To assign them, the model needs to know which tokens are image tokens, via mm_token_type_ids.

Here's the trap. TRL's GRPO and GKD loss paths were written for text and forward the model without mm_token_type_ids; Qwen3.5's get_rope_index then either errors or mis-positions. And you can't just reuse the tensor from generation — the loss runs on cat(prompt, completion), a different length. The repo's fix recomputes it from the actual input_ids of that forward:

# src/vlm_workshop/distill.py — recompute per forward (image pads → 1, text → 0)
mm_token_type_ids = (input_ids == image_pad_id).long()

It's one line, but finding it is the difference between a run that silently learns nothing and one that works. Multimodal training is mostly this kind of plumbing.

Section 10 · Self-distillation

SDFT — the model teaches itself

§10with model.disable_adapter(): is the whole trick — no second model in memory, just the base weights acting as a teacher because they get to see the answer.

Distillation needed a separate teacher. SDFT removes it: the student generates from the plain prompt; the self-teacher is the same model with the LoRA adapter disabled, but shown the gold answer in context. Seeing the answer, the base assigns high probability to the right tokens, and a JSD pulls the student toward that. The only difference between the two forwards is the demonstration:

The loss, and why it resists forgetting

The objective is the same JSD as GKD, but the teacher is the model's own base weights conditioned on the demonstration:

ℒSDFT=JSD(pbase(·∣prompt,gold)∥pθ(·∣prompt))

Because the target is the base model's own (demonstration-informed) belief rather than a hard label, the student is pulled toward a distribution it already nearly holds — a small, safe step that teaches the task without dragging the weights far from their general-purpose start. Go deeper: how the numbers are made (evaluation)

Every prediction and gold JSON is flattened to a multiset of (leaf-key, normalized-value) pairs — list indices dropped, so repeated line-items share a key like menu.nm. From that: field_f1 (F1 over leaf keys — did it find the fields), pair_f1 (F1 over key+value — the headline), and value_acc (of shared keys, fraction with the right value). Values are normalized (lowercase, strip commas/currency, canonicalize numbers) so 1,000.00 == 1000. Decoding is greedy for eval so the number is deterministic. SROIE (flat) and CORD (nested) are scored by the exact same code and reported separately, then macro-averaged.

Glossary

Token / embedding
A piece of text (or an image patch) mapped to a vector; the model operates on the vector sequence.
Attention head
One parallel "lookup" — a set of query/key/value projections. Models run many in parallel.
KV-cache
Stored keys/values from past tokens so generation adds O(1) work per new token.
LoRA
Low-Rank Adaptation — train a small BA update beside frozen weights (~1% of params).
pair_f1
F1 over (key, value) pairs of the extracted JSON — the headline correctness metric.
On-policy
Training on sequences the current model itself generated (GRPO, GKD, SDFT), vs. teacher-forced gold (SFT).
JSD / KL
Divergences between two distributions; KL is asymmetric (mode-covering vs mode-seeking), JSD is its symmetric blend.
Appendix

Derivations & engineering notes

A · RMSNorm, in full
RMSNorm(x)=x1d∑i=1dxi2+ε⊙g

No mean-subtraction and no bias (unlike LayerNorm) — just rescale by the root-mean-square, then a learned per-channel gain g. Cheaper, and empirically as good for transformers.

B · Cross-entropy with the -100 mask

PyTorch's cross-entropy skips any target equal to ignore_index=-100. Setting a label to -100 therefore removes that position from both the loss and its gradient — which is exactly how "supervise the answer only" and "never train on image/pad tokens" are implemented. Labels are the inputs shifted left by one (next-token prediction), with the last position dropped.

C · The generalized JS divergence (GKD/SDFT)

With m=βt+(1−β)s a mixture of teacher and student, the generalized JSD interpolates between the two KL directions. β→0 is forward KL KL(s∥t) (mode-seeking for the student), β→1 is reverse KL(t∥s) (mode-covering), and β=0.5 the symmetric JSD. For low-entropy structured-JSON outputs the direction barely mattered (0.838–0.847 in the sweep).

D · The engineering reality: vLLM, Blackwell, and rollouts

GRPO/GKD need fast sampling. The obvious tool is vLLM — but vLLM 0.24 (the only version supporting Qwen3_5) is a CUDA-13 build, and this workstation is a Blackwell GPU on a CUDA-12.8 driver with no forward-compat path, so vLLM won't load. The repo falls back to TRL's transformers-backend rollouts (use_vllm=False); a 4B model plus short receipt JSON keeps that cheap enough.
